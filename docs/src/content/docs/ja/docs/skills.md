オプトインの **Docs** ファミリは、heal の Claude Code プラグインにある 2 つのスキルで扱います。docs オブザーバが読む doc ⇔ src の対応表を作る `/heal:setup` の docs の手順と、ページそのものに手を入れる `/heal:docs` です。プラグインの入れ方は [Code › スキル](/heal/ja/code/skills/) を参照してください。

## `/heal:setup docs` — ファミリを有効にして docs と src を対応付ける

`[features.docs]` を有効にし(対象にするドキュメントの glob はリポジトリに合わせて決めます)、どのドキュメントがどのソースファイルを説明しているかの一覧 `.heal/doc_pairs.json` を書きます。heal はこのファイルを読むだけで、作るのはあなたが頼んだときのセットアップスキルの役目です。ファイルが無いときや、もう存在しないパスを含むときは `heal doctor` が docs を `todo` と報告するので、`/heal:setup` がこの手順をもう一度提案します。

ペアの見つけ方は **3 つ**あります。

| 方法          | ペアの見つけ方                                                                                                       |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Mention**   | ドキュメント本文が `path/to/source.rs` か、1 つの src ファイルに解決するバッククォートで囲んだ識別子を参照している。 |
| **Mirror**    | ディレクトリ構成が対応している: `docs/payments/engine.md` ↔ `src/payments/engine.ts`。                               |
| **LLM**(任意) | 上の 2 つで見つからないときに、Claude がドキュメントと候補のソースを読む。実行の前に確認します。                     |

どのペアにも見つけ方が記録されます。手で追加したペア(`source: "manual"`)は、何度再実行してもそのまま残ります。書き込むのは `.heal/doc_pairs.json`(と、ファミリを初めて有効にするときの `.heal/config.toml`)だけです。

## `/heal:docs` — ドキュメントを見直して直す

ドキュメント版の `/heal:refactor` です。docs の Finding を読み、変更を提案し、あなたが承認したものだけを 1 提案 1 コミットで適用します。push や pull request の作成はしません。

1. **診断** — `heal status --all --feature docs --json`、doc pairs、docs の設定を読み、指摘されたページを、それが説明しているソースと一緒に読みます。各ページは **Diátaxis** の目的(チュートリアル・ハウツー・リファレンス・解説)で分類します。ドリフトがどれだけ効くかは目的で決まるからです。リファレンスやチュートリアルの手順が古いと読者を迷わせますが、解説ページが少し古くても多くの場合は問題になりません。
2. **提案** — ドキュメントのどこが傷んでいるかを短くまとめ、優先度の高い Finding から番号付きで提案します。
3. **選択** — どの提案を適用するかをあなたが選びます。
4. **適用** — 1 提案につき 1 コミット。コミットの前に、サイトのビルド(プロジェクトにあれば)とリンクの再確認を行います。
5. **報告** — 変えたものと、残っているものをまとめます。

Finding ごとの主な提案:

| メトリクス        | よくある提案                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------- |
| `doc_link_health` | 名前が変わった・移動したページにリンクを向け直す。候補が複数あるときは確認する。                   |
| `doc_drift`       | 名前が変わった識別子を置き換える。概念そのものが無くなった・作り直されたときは、その節を書き直す。 |
| `doc_freshness`   | ソースから離れてしまった節を、今のコードをもとに書き直す。                                         |
| `doc_coverage`    | コードから事実が取れるなら足りないページを書く。ページが要らないならペアを外す。                   |
| `orphan_pages`    | 読者が探すセクションからリンクする、アーカイブに移す、または退役させる。                           |
| `todo_density`    | コードや設定で答えが出た TODO を埋める。答えの出ていない問いは、あなたが決めることとして挙げる。   |

1 件ずつの修正だけでなく、根拠がそろっていれば**構造的な変更**も提案します。目的が混ざったページ(リファレンスの中のチュートリアルなど)を分ける、複数のページで説明している概念を 1 つの正典ページにまとめる、読者が探すセクションにページを移す、誰も必要としないページを退役させる、といったものです。どのページに説明を残すか、古いページを書き直すか退役させるか、のような編集上の判断は、具体的な選択肢を付けて質問します。

**やらないこと:** `doc_coverage` を消すためだけの空のページは作りません(空のページは無いより悪い)。古い名前を意図して書いている変更履歴・移行ガイド・引用を「そろえる」こともしません。ドキュメントに合わせてコードを変えることもしません — 正しいのはソースで、直すのはドキュメントです。

**[Semantic (Jev)](/heal/ja/semantic/) を有効にしている場合**は、Jev が付けたページの種類、複数の文書が同居したり目的が混ざったりしているページ(`doc_structure`)、置き場所の違うページ(`doc_placement`)、コードが裏付けなくなった記述(`doc_drift.semantic`)、2 回説明されている・食い違っている・どこにも説明がない概念(`doc_concept`)も使います。

引数: パスを渡すとその下の Finding に絞り、Finding の id を渡すとその Finding に絞り、`plan` を渡すと提案までで止まります。

トリガーフレーズ: 「review the docs health」、「fix the doc findings」、「docs are out of date」、「/heal:docs」。

## `/heal:docs scaffold` — ドキュメントツリーをゼロから組む

ドキュメントがほとんど無いプロジェクト向けです。コードベースのシグナルだけからドキュメントツリーを組み立て、何度実行しても安全です。出力は `[features.docs] scaffold_root`(既定 `.heal/docs/`)の下に Markdown で置かれ、コミットはしません。

- **対話ではなく検出で決める。** どのページを書くかは検出したシグナルだけで決まります。出来上がりを見て、要らないページは消してください。
- **厳しい出力条件。** コードベースから意味のある中身を埋められるページだけを書きます。基礎的なページ(README、Wiki Index、System Context、Architecture Overview、Glossary、Getting Started)は常に書き、条件付きのページは条件を満たしたときに書きます。組織的なページ(Quality Goals、Roadmap、Runbooks、SLOs、Postmortems、Security Posture)は**初回には書きません** — 材料がそろってから書いてください。
- **実際のシグナルから埋める。** マニフェストからコンテナ一覧、ドキュメントコメントからモジュールの責務、公開シンボルから用語集の種、CI 設定からコントリビュートのルール、マイグレーションから ER 表を作ります。自信を持って埋められないものは入れません — 担当者名や SLO の数値を作り出すことはしません。
- **`TODO(human):` は 1 ファイルだけ** — ADR のテンプレート(`decisions/0000-template.md`)です。
- **再実行できる。** 既定では自動管理の節を今のシグナルで更新し、あなたの編集は残します。`--missing-only` は新しいファイルを足すだけ、`--force` はページを作り直します。

ページの一覧は、Diátaxis(目的)、arc42(アーキテクチャの節)、C4 モデル(ズームの段階)、戦略的 DDD(境界づけられたコンテキスト)、ADR(意思決定の記録)、SRE(運用ページ)、DeepWiki(AI が書いた Wiki に見られる傾向)を組み合わせたものです。`[features.docs]` を有効にする前でも動き、ファミリを有効にした時点で出力が観測対象に入ります。

トリガーフレーズ: 「scaffold the docs tree」、「generate the wiki」、「build the documentation from scratch」、「/heal:docs scaffold」。
